# Unidad 12 — node_modules

## Objetivos

- Entender qué es la carpeta `node_modules` y cuándo se crea.
- Diferenciar dependencias directas de dependencias transitivas.
- Comprender cómo Node.js localiza un módulo (module resolution).
- Saber por qué `node_modules` pesa tanto y por qué no se sube a Git.
- Aplicar buenas prácticas de uso y mantenimiento de esta carpeta.

## Requisitos

- Haber ejecutado `npm install` al menos una vez en un proyecto.
- Tener una idea básica de qué es `package.json`.
- Haber visto alguna vez una estructura de carpetas de proyecto en la terminal o en el explorador.
- (Recomendado) Haber completado la Unidad 11 sobre scripts, porque veremos `node_modules/.bin`.

```text
mi-proyecto/
```

## ¿Qué hay realmente dentro?

## ¿Qué es node_modules?

Es la carpeta donde el gestor de paquetes instala todas las dependencias del proyecto (todo el código de terceros que tu aplicación necesita para funcionar).

Por ejemplo:

```bash
npm install react
```

Después aparecerá:

```text
node_modules/
└── react/
```

Pero React no viene solo.

También instala otras librerías de las que depende:

```text
node_modules/
├── react/
├── scheduler/
├── loose-envify/
├── js-tokens/
└── ...
```

### Una analogía

Imagina que construyes una casa.

Necesitas:

- ladrillos
- cemento
- puertas
- ventanas

Cuando compras el material lo guardas en un almacén.

Ese almacén sería:

```text
node_modules
```

Mientras construyes, vas utilizando ese material. Nadie construye una casa llevando el cemento en la mano desde la fábrica: primero lo acumulas en tu almacén. Hace lo mismo npm con tu proyecto.

## ¿Cuándo se crea?

No existe desde el principio.

Supongamos este proyecto:

```text
mi-proyecto/
└── package.json
```

Ejecutamos:

```bash
npm install
```

Entonces ocurre:

```text
package.json
   ↓
npm
   ↓
Descarga paquetes
   ↓
Crea node_modules
```

Es decir: sin un `package.json` con dependencias (y sin ejecutar la instalación), la carpeta simplemente no está ahí.

## ¿Quién la crea?

Nunca la creamos nosotros a mano.

La crean automáticamente los gestores de paquetes:

- npm
- pnpm
- Yarn

Nosotros únicamente ejecutamos comandos; la carpeta es un resultado, no un archivo que escribas.

## ¿Qué contiene?

Aquí aparece un error muy común.

Muchos creen que solo contiene las librerías que instalaron.

Por ejemplo:

```bash
npm install axios
```

Piensan que aparecerá únicamente:

```text
node_modules/
└── axios/
```

Pero no.

### Dependencias transitivas

Axios depende de otras librerías.

```text
Axios
   ↓
follow-redirects
```

Así que npm instala ambas:

```text
node_modules/
├── axios/
└── follow-redirects/
```

Ahora imagina una aplicación React:

```text
React
   ↓
Paquete A
   ↓
Paquete B
   ↓
Paquete C
```

Cuando instalas React realmente estás instalando un árbol de dependencias completo, no un único paquete aislado.

### Dependencias directas

Son las que tú instalas a mano, las que aparecen en tu `package.json`.

Ejemplo:

```bash
npm install react axios
```

```text
Proyecto
├── React
└── Axios
```

### Dependencias transitivas

Son las dependencias de tus dependencias: llegan solas, sin que tú las pidas.

```text
Proyecto
├── React
│
│   ├── Scheduler
│
│   └── Loose-envify
│
└── Axios
    │
    └── Follow-redirects
```

Tú nunca escribiste:

```bash
npm install scheduler
```

Sin embargo, está instalado.

Porque React lo necesita.

## ¿Cómo encuentra Node.js un módulo?

Supongamos este código:

```javascript
import React from "react";
```

¿Cómo sabe Node.js dónde está React?

No existe una ruta.

No escribimos:

```javascript
import React from "./node_modules/react";
```

Entonces...

¿cómo lo encuentra?

### Module Resolution

Node.js sigue un algoritmo muy preciso llamado *module resolution* (resolución de módulos).

Supongamos esta estructura:

```text
mi-proyecto/
│
├── node_modules/
│      └── react/
│
└── src/
       └── App.js
```

Cuando encuentra:

```javascript
import React from "react";
```

hace algo parecido a esto:

```text
¿Existe node_modules?
   ↓
Sí
   ↓
¿Existe react dentro?
   ↓
Sí
   ↓
Lo carga
```

### ¿Y si no lo encuentra?

Sube un nivel y vuelve a buscar:

```text
Proyecto
   ↓
node_modules
   ↓
No existe
   ↓
Sube una carpeta
   ↓
Busca otro node_modules
```

Este comportamiento permite reutilizar dependencias en algunas estructuras de proyectos, como los monorepos (donde varias aplicaciones comparten una misma carpeta de paquetes en la raíz).

### ¿Qué archivo carga?

Supongamos:

```text
react/
├── package.json
├── index.js
└── ...
```

Node primero abre:

```text
package.json
```

Busca:

```json
{
  "main": "index.js"
}
```

o

```json
{
  "exports": {}
}
```

Y entonces sabe cuál es el archivo de entrada de esa librería: por eso cada paquete trae su propio `package.json`, que funciona como su "carta de presentación" interna.

## ¿Por qué pesa tanto?

Esta es probablemente la pregunta más frecuente.

Imagina esto.

Instalas:

```bash
npm install react
```

No ocupa únicamente React. Instalas:

- React.
- Sus dependencias.
- Las dependencias de esas dependencias.
- Las dependencias de esas dependencias...

El árbol puede crecer rápidamente.

Por ejemplo:

```text
Proyecto
   ↓
React
   ↓
20 paquetes
   ↓
100 paquetes
   ↓
250 paquetes
```

Cada uno contiene:

- JavaScript.
- Archivos de configuración.
- Tipos de TypeScript.
- Licencias.
- Documentación.
- Recursos adicionales.

### Un ejemplo real

Un proyecto recién creado con Vite y React puede contener cientos de paquetes en `node_modules`, aunque tú solo hayas instalado unas pocas dependencias de forma explícita.

No significa que hayas hecho algo mal: es consecuencia del árbol de dependencias que necesita el ecosistema moderno.

## ¿Por qué no se sube a Git?

Supongamos:

```text
Proyecto
│
├── node_modules/
└── package.json
```

Si haces:

```bash
git add .
```

Subirías miles de archivos.

Esto tiene varios problemas:

- El repositorio crecería enormemente (cientos de megas o más).
- Los clones serían mucho más lentos para todo el equipo.
- Se versionarían archivos generados automáticamente, que no son "tu" código.
- Es redundante: cualquier desarrollador puede recrearlos con `npm install` o `pnpm install`.

Por eso `node_modules` aparece casi siempre en `.gitignore`:

```text
node_modules/
```

## ¿Qué pasa si la borramos?

Nada grave.

Puedes eliminarla completamente.

Después ejecutar:

```bash
npm install
```

o

```bash
pnpm install
```

Y el gestor volverá a crearla a partir de la información de `package.json` y del archivo de bloqueo (`package-lock.json` o `pnpm-lock.yaml`).

Esto demuestra que `node_modules` es un artefacto generado, no una parte del código fuente: es desechable y reconstruible en cualquier momento.

## ¿Qué problemas tiene node_modules?

Aunque funciona muy bien, tiene algunas limitaciones.

Por ejemplo:

- Puede ocupar mucho espacio en disco.
- Dos proyectos distintos pueden almacenar copias de la misma dependencia (una copia por proyecto, sin compartir).
- La estructura puede llegar a ser muy grande y lenta de recorrer.

Precisamente estos problemas motivaron la aparición de gestores como pnpm, que estudiaremos más adelante y que reutiliza un único almacén de paquetes para todos tus proyectos.

## Buenas prácticas

- No modifiques archivos dentro de `node_modules`; cualquier reinstalación sobrescribirá esos cambios.
- No subas `node_modules` al repositorio Git: siempre debe estar en `.gitignore`.
- Si aparecen errores extraños relacionados con dependencias, una solución habitual es borrar `node_modules` y reinstalar.
- Recuerda que la carpeta se genera automáticamente y no forma parte del código fuente: lo que debes versionar es `package.json` (y el lock file).

## Conceptos clave

- `node_modules` contiene todas las dependencias necesarias para el proyecto.
- Incluye tanto dependencias directas (las que tú instalas) como transitivas (las de tus dependencias).
- Node.js utiliza un algoritmo de resolución de módulos para encontrar los paquetes, subiendo de nivel si no los encuentra.
- El archivo `package.json` de cada paquete indica cuál es su punto de entrada (`main` o `exports`).
- El gran tamaño de `node_modules` se debe al árbol completo de dependencias.
- Es una carpeta generada automáticamente: se borra y se recrea con `npm install`, y no debe versionarse con Git.
